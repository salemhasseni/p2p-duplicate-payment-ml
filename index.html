Risk Predictor

A machine learning classifier that scores every open purchase order by duplicate payment risk — using only signals available before any payment executes, so AP teams can intervene in advance rather than reconcile after the fact.

Author: Salem Hasseni

01 — The Problem

A €2.39M control gap running silently for 30 months

The Project 1 OCPM audit of SAP P2P data spanning April 2022 to October 2024 surfaced one finding with a clear financial cost: 188 payment objects were executed between 2 and 5 times each, generating €2.39M in gross duplicate payment exposure across 1,598 purchase orders — and no automated control flagged a single one.

The dataset covers 14,671 events across 9,543 objects of 7 types — purchase orders, purchase requisitions, goods receipts, invoice receipts, payments, requests for quotation, and PO items — in OCEL 2.0 format. The Project 1 audit recommended a Celonis Alert as a quick win. This project builds the risk-scoring layer that sits beneath it.

The anomaly is visible in the event counts. Execute Payment fires only 1,166 times across 1,598 POs — fewer than one per order on average — yet some POs accumulate multiple executions. That asymmetry is what this model targets.

02 — Approach

From audit finding to production-ready ML pipeline

The model operationalizes the audit finding through four stages. The core design constraint throughout: every feature must be computable before Execute Payment fires on a given PO. Anything that could only be known after payment execution is not a predictor — it is leakage.

01

Label derivation from the OCEL object graph

Target variable derived from the payment object dimension — consistent with Project 1 methodology. A PO is labelled positive if any linked payment object was executed more than once. Result: 315 positive labels (19.7%) across 1,598 POs. Class balance is suitable for a binary classifier without resampling.

02

Two rounds of leakage detection and removal

Three candidate features were identified as post-execution proxies and removed before any model was trained. Each required class-stratified mean analysis to surface: features whose means differ between classes only because they reflect the outcome, not behaviour that precedes it.

03

Feature engineering from process timing and payment attributes

Ten leakage-free features: four timing deltas across the PO lifecycle (creation → approval → goods receipt → payment), goods receipt count and spread, approval lag, and two payment object attributes — amount and method — confirmed as pre-execution signals via invoice correlation (difference = 0.0 across all 1,598 POs).

04

Random Forest classifier with stratified evaluation

200 trees, max depth 6, class_weight='balanced' to compensate for the 80/20 class split. Stratified 80/20 train-test split preserves the 19.7% positive rate in both partitions. Evaluation on ROC-AUC, precision, recall, and full confusion matrix.

03 — Feature Engineering

What was kept, what was cut, and why it matters

Feature engineering on an anonymised log is a leakage minefield. Three features were discovered and removed across two separate iterations — not upfront, but only after training produced suspiciously strong results that collapsed under scrutiny.

Leakage detection methodology

For each candidate feature, compute the class-stratified mean across the training set. If a feature's mean is significantly elevated for the positive class in a way that can only be explained by post-execution data — it is a proxy for the label, not a predictor. All three removed features failed this test.

Removed — data leakage

✕ payment_count ✕ payment_gap_days ✕ event_count

payment_count and payment_gap_days were direct post-execution counts. event_count was subtler: it looked behavioural, but stratified analysis showed it was inflated on duplicate-risk POs because repeated Execute Payment events added to the per-PO total. A label proxy disguised as a process metric.

Kept — confirmed pre-execution signals

✓ pay_amount ✓ po_to_payment_days ✓ po_to_last_gr_days ✓ gr_to_payment_days ✓ approval_to_payment_days ✓ approval_lag_days ✓ gr_spread_days ✓ goods_receipt_count ✓ pay_method_C ✓ pay_method_D

pay_amount verified: equals the invoice credit amount on every single PO — max difference 0.0, correlation 1.000 across all 1,598 rows. Recorded at invoice creation, before any payment executes. Legitimate pre-payment signal.

Feature Importance — Mean Decrease in Impurity

pay_amount leads at 0.279 — higher-value orders carry measurably higher risk, consistent with €2.39M concentrating in only 188 payment objects. The four timing features cluster between 0.10–0.14, suggesting process velocity carries weak but real signal. Bank Collection (pay_method_C) shows proportionally higher duplicate risk than Bank Transfer or Direct Debit.

04 — Results

Evaluation on the held-out test set

320 POs held out for evaluation, stratified to preserve the 19.7% positive rate. The model achieves meaningful discrimination above chance on a dataset where the three highest-signal features — vendor identity, AP user ID, and document type — are entirely absent due to anonymisation.

Why the ceiling is at 0.60 — and what it signals

After removing three leaking features, the remaining signal is genuinely weak. The duplicate payment pattern does not manifest as a detectable process deviation in timing, structure, or payment method. It distributes evenly across all process variants — characteristic of a systemic control failure, not an operator error pattern. Duplicates ran undetected across all 5 purchasing groups for 30 months. In a live SAP extraction, vendor identity and AP user alone would likely push AUC above 0.80.

05 — Production Roadmap

What this becomes in a live Celonis environment

The model output — a risk score per open PO — maps directly to the Celonis Alert recommended in Project 1. Deployment follows four steps in the Celonis platform: SAP ECC feature extraction, nightly scoring via the ML Workbench, AP supervisor queue routing through Action Flows, and quarterly retraining as confirmed duplicates accumulate.
